# Decisions (ADR-lite)

Settled choices. Don't re-litigate during the build; add a new entry if something must change.

| # | Decision | Why | Revisit when |
|---|---|---|---|
| 1 | Dagster OSS via Helm on AKS, not Dagster+ | The POC is specifically about self-hosting on AKS; Dagster+ hybrid would remove the thing being proven. | Company prefers managed control plane. |
| 2 | One AKS cluster, two namespaces | Cost. Env boundary is already fully expressed in Helm values; moving to two clusters is a kube-context change. | Corporate requires cluster-level isolation. |
| 3 | Azure Database for PostgreSQL Flexible (burstable B2s, centralus) over in-cluster Postgres | Durable Dagster state across cluster delete/recreate; matches what IT will expect; ~$6/mo stopped. B1ms/B-series were unavailable in eastus2. | Never for this POC. |
| 4 | Serverless Databricks compute only (Pipes-submitted job + SQL warehouse) | $0 idle, no VM cost, no cluster plane networking to design yet. | Corporate forbids serverless or needs classic SCC in their VNet. |
| 5 | **Revised.** Bronze ingestion is a serverless notebook task submitted with `PipesDatabricksServerlessClient`; dbt builds the bronze table from the landing volume. (Originally: an SDP pipeline triggered via `pipelines.start_update`, not Pipes.) | An API-to-JSON fetch is plain Python, so Pipes fits and gives metadata and logs in Dagster. Azure serverless has no FUSE, so custom SDK-based Pipes classes are used (see [Dagster Pipes](concepts/dagster-pipes.md#gotchas)). | Ingestion becomes declarative/streaming; then reconsider SDP. |
| 6 | dbt runs inside the Dagster run pod via `dagster-dbt`, against a serverless SQL warehouse | Simplest lineage integration; one image. | dbt runtime grows; move to Databricks dbt task launched via Pipes. |
| 7 | Databricks Asset Bundles for all Databricks code; Terraform for Databricks *infra* (catalog, SP, warehouse, grants) | Bundles are the native deploy unit for code; Terraform for long-lived objects. Clear line: if it has a `-t <env>` target, it's a bundle. | — |
| 8 | Terraform for Azure; Helm for Dagster; no Terraform-managed Helm releases | Keeps image promotion in CI, not in Terraform state. | — |
| 9 | GitHub + Actions + Environments | Free, OIDC to Azure, environment gates built in. | Company is on Azure DevOps — translate workflows; structure unchanged. |
| 10 | Public-but-gated control planes; no private endpoints/VPN in POC | ~$300/mo saved; zero application-code impact when added later. See [corporate-migration.md](corporate-migration.md). | Moving into corporate network. |
| 11 | Databricks SP with OAuth M2M secret in Key Vault | Works everywhere today. Upgrade path: federate `id-dagster-<env>` as the SP identity, drop the secret. | Phase 6 or corporate. |
| 12 | Managed-VNet Databricks workspaces (no VNet injection) | Serverless doesn't need it; VNet injection matters for classic compute, which isn't used. Subnets reserved anyway. | Classic compute or corporate requirement. |
| 13 | One Unity Catalog metastore, catalogs `stage`/`prod` | UC is one metastore per region; env isolation is at catalog level, which is also how corporate UC deployments usually work. | Company already has a metastore — attach workspaces to it. |
| 14 | Region `eastus2` (Postgres in `centralus`, AKS VM `Standard_D2as_v6`) | Serverless SQL availability and price; burstable Postgres and B-series VMs weren't available in eastus2 on the trial subscription. | Company region. |
| 15 | Dagster is now owned by Prefect (acquisition July 2026); OSS continues under same license, Dagster+ continues | No action; noted for IT questions. | Roadmap announcements. |
| 17 | User deployment memory limit 1Gi (shared with run pods) | Dagster's `includeConfigInLaunchedRuns` (enabled by default) propagates the user deployment's `resources` to run pods. Run pods import the Databricks SDK + dbt at runtime and need more than the 316Mi the gRPC server uses at rest. Raising the user deployment limit to 1Gi covers both. | Decouple run pod resources from user deployment by setting `runK8sConfig.containerConfig.resources` on the user deployment — this overrides only the run pod resources without disabling `includeConfigInLaunchedRuns`. Do this when run pod memory needs diverge from the gRPC server, e.g. more dbt models or heavier Databricks work. |
| 16 | Self-hosted runners via ARC on AKS, not GitHub-hosted runners | GitHub-hosted runners have dynamic IPs that are blocked by the AKS authorized IP ranges and Databricks workspace IP ACL. Three options were evaluated: **(a) GitOps (Flux/ArgoCD)** — Microsoft's recommended pattern for pure-Kubernetes deployments, but doesn't help with Databricks bundle deploy (non-Kubernetes API call); **(b) ARC (Actions Runner Controller)** — runner pods inside AKS have direct API server access and egress through the AKS IP (already on the Databricks allow list), solving both problems with one mechanism; **(c) `az aks command invoke`** — works as an escape hatch but is not a full CI/CD pattern. ARC was chosen because the POC deploys to both AKS (Helm) and Databricks (bundle CLI), and ARC handles both from a single runner. Eliminates all temporary IP whitelisting steps and their ~4 min overhead per deploy. $0 incremental cost — runs on the existing AKS node, scales to zero when idle, and self-hosted runners have no GitHub Actions per-minute charges. | Move to GitOps (Flux) if Databricks deploys move to a Kubernetes-native mechanism, or if corporate requires pull-based deployments. |
